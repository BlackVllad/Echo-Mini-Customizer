💀 Diagrama 1 — Cómo HIFIEC21_BRICKED brickeó el Echo Mini
Entrada
HIFIEC20.IMG abierto en EchoMiniCustomizer
Tamaño: 56 MB  |  Temas: 5  |  part5_size = 0x2B700D0  |  fw_end = 0x3530000
Acción del usuario
Click en "Expandir a 6 temas" en la GUI
⚠ Bug 1 — Cálculo incorrecto de part5_size
El código calculaba el nuevo tamaño de la parte 5 como:
new_p5_end = (meta_tabla_fin - part5_offset) # solo llega hasta el fin de la tabla de metadatos
Esta fórmula ignora que los datos de imagen de los temas B–E viven después de la tabla → el valor calculado era ~22 MB en lugar de 45 MB
⚠ Bug 1 — Consecuencia: part5_size sobrescrito
Sin la protección max(calculado, original) el código sobrescribía part5_size con el valor incorrecto.
En la versión que generó el archivo brickeado, un error adicional produjo: part5_size → 0x341CC3C (54 MB) — mayor al real de 45 MB.
La diferencia de ~9 MB era relleno de ceros vacíos al final del archivo.
Propagación — _fix_integrity hereda el error
_fix_integrity() usa part5_size para recalcular fw_end:
p5_end = part5_offset + part5_size # 0x9B5998 + 0x341CC3C = 0x3DD25D4 fw_end = redondear_arriba(p5_end) # → 0x3DE0000 (64.7 MB) ← INCORRECTO # correcto era: fw_end = 0x3530000 (55.6 MB)
Resultado — Archivo .IMG corrupto
• El archivo creció de 56 MB → 65 MB (9 MB de ceros vacíos añadidos)
• El trailer C6 18 C6 18 fue sobreescrito con 00 00 00 00 — ver detalle abajo
• fw_end = 0x3DE0000 apunta a una dirección fuera de la partición firmware
• Archivo guardado como HIFIEC21.IMG
⚠ ¿Por qué importa el trailer C6 18 C6 18?
📌 ¿Qué es el trailer?
Los últimos 4 bytes de cualquier .IMG de Rockchip RKnano son un sello de integridad — en este firmware vale C6 18 C6 18 (patrón repetido de 2 bytes). Algunos bootloaders lo usan como comprobación rápida de formato: si los últimos 4 bytes son 00 00 00 00, el archivo se considera truncado o corrupto y se rechaza antes incluso de verificar el header.
🔍 ¿Por qué se pierde al expandir el archivo?
_fix_integrity() extiende el archivo añadiendo ceros al final antes de intentar preservar el trailer. La secuencia errónea era:
1. El archivo original termina en: [ ... datos ... | C6 18 C6 18 ] ← trailer correcto 2. Se añaden 9 MB de ceros: [ ... datos ... | C6 18 C6 18 | 00 00 ... 00 00 ] 3. saved_trailer = data[-4:] # lee los NUEVOS últimos 4 bytes → 00 00 00 00 ← ya tarde 4. data[-4:] = saved_trailer # restaura 00 00 00 00 → trailer perdido
💥 ¿Qué consecuencia tiene en el dispositivo?
Junto con el fw_end erróneo, el bootloader del Echo Mini enfrenta dos señales de firmware inválido simultáneamente:
  ① fw_end fuera del rango de flash → no encuentra la copia del header
  ② Trailer 00 00 00 00 → el archivo parece truncado o sin terminar
Cualquiera de los dos sería suficiente para rechazar el firmware al arrancar.
✅ Cómo se corrigió:
El fix guarda el trailer antes de cualquier redimensionamiento:
1. saved_trailer = bytes(data[-4:]) # guarda C6 18 C6 18 ANTES del resize 2. Se añaden/recortan bytes según fw_end 3. Se escribe copia del header en fw_end 4. data[-4:] = saved_trailer # restaura C6 18 C6 18 al final ✓

🔗 ¿Por qué importa cada uno de esos campos?
part5_size — offset 0x150 en el header
¿Qué es? Le dice al dispositivo cuántos bytes ocupa la partición 5 (part5), que contiene todas las imágenes y recursos del firmware: fondos, iconos, animaciones de boot, carga y apagado.

¿Por qué creció de 45 MB a 54 MB en el archivo brickeado?
El código antiguo llamaba a _allocate_part5_space() para cada una de las 306 imágenes de UI del nuevo tema F, copiando datos de píxeles reales al final de part5. Esas imágenes existían porque el usuario las había importado previamente. Resultado: se añadieron ~9 MB de datos de imagen reales, no ceros.
📊 Verificado por análisis binario del HIFIEC21_BRICKED:
  • 306 de 307 entradas de UI del tema F apuntaban a offsets más allá del final de HIFIEC20 (región nueva)
  • El contenido en esas posiciones eran datos de imagen reales (3.27 MB de 8 MB no eran ceros)
  • Resolución típica: 320×170 px a 16-bit = 108,800 bytes por imagen
  • data == ThemeA: False → imágenes propias del tema F importadas por el usuario
↓   part5_size incorrecto se propaga directamente al cálculo de fw_end
fw_end — offset 0x1F4 en el header
¿Qué es? Puntero que indica al bootloader dónde leer la copia del header en la NAND flash. Al arrancar, el bootloader salta a esa dirección y compara los 512 bytes que encuentra con el header principal — si no coinciden, el firmware es rechazado.

¿Cómo lo calcula _fix_integrity?
# Con part5_size INCORRECTO (archivo brickeado): p5_end = part5_offset + part5_size = 0x9B5998 + 0x341CC3C = 0x3DD25D4 fw_end = redondear_64KB(p5_end) = 0x3DE0000 (64.7 MB) ← excede la flash # Con part5_size CORRECTO (archivo fijo): p5_end = part5_offset + part5_size = 0x9B5998 + 0x2B700D0 = 0x3526A68 fw_end = redondear_64KB(p5_end) = 0x3530000 (55.6 MB) ✓
↓   fw_end incorrecto obliga a extender el archivo más allá del límite del dispositivo
Tamaño del archivo .IMG
¿Por qué importa el tamaño? El Echo Mini tiene una partición de firmware en su NAND flash con capacidad fija. El HIFIEC20 original de 56 MB encajaba correctamente. Con 65 MB ocurre la siguiente cadena de fallos al intentar arrancar:

  ①  El archivo excede el espacio reservado para el firmware — los últimos 9 MB se escriben fuera de la partición o se truncan.
  ②  La copia del header en 0x3DE0000 (64.7 MB) queda en una dirección que el bootloader no puede leer correctamente.
  ③  Verificación de integridad: FALLA → dispositivo brickeado.

¿Por qué el HIFIEC21 corregido sigue siendo 56 MB si el tema F tiene imágenes?
El código nuevo crea entradas de metadatos para el tema F que referencian los mismos offsets de imagen del tema A sin copiar píxeles. El usuario puede después importar sus propias imágenes para el tema F desde la GUI — esa importación sobreescribe los píxeles en su lugar original sin agrandar el archivo.
Bug 1 identificado — part5_size nunca debe reducirse
En expand_theme_count() la fórmula solo consideraba el fin de la tabla de metadatos, ignorando datos de imagen que viven después de la tabla en esta versión del firmware.
new_p5_end = (meta_abs + new_count * 108) - part5_offset # ↑ solo cubre hasta el fin de la tabla → puede truncar o sobrestimar
✅ Fix Bug 1 — Protección con max()
new_p5_end = max( (meta_abs + new_count * 108) - part5_offset, # tabla self.part5_size # original ) # part5_size NUNCA puede ser menor al valor original del firmware
También aplicado en patch_for_themed_boots() que tenía el mismo bug.
Bug 2 identificado — boot data de temas existentes sobreescrita
El loop de expansión usaba shared_r26 (imágenes de boot del tema A) para todos los bloques de boot, incluyendo temas B–E que ya tenían sus propias imágenes personalizadas de boot, carga y apagado almacenadas en offsets únicos.
✅ Fix Bug 2 — Preservar entradas propias de cada tema existente
# Para temas ya existentes (0 < t_idx < current_n): new_r26.append(shared_r26[i]) # ← usaba siempre tema A src_idx = t_idx * new_blk + i # ← lee la entrada real del tema new_r26.append(part5[r26_start + src_idx*16 : ...])
Cada tema B–E conserva sus imágenes únicas de boot/carga/apagado.
✅ Fix adicional — Preservación del trailer
_fix_integrity() ahora guarda los últimos 4 bytes antes de redimensionar el archivo y los restaura al final:
saved_trailer = bytes(data[-4:]) # guardar antes de resize ... # resize + escribir copia de header data[-4:] = saved_trailer # restaurar siempre
