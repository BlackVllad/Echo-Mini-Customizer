§2 — Campos del Header (0x000–0x1FF)

OffsetTamañoNombreValor (HIFIEC20 orig.)Descripción

0x1504 B part5_size 0x02B700D0 (45 MB) Tamaño de PART5. CRÍTICO: debe permanecer ≤ original. Si crece incorrectamente, fw_end excede la flash → brick
0x1F44 B fw_end 0x03530000 (55.6 MB) Dirección donde el bootloader espera encontrar la copia del header. Si excede la flash (≈57 MB) → brick

fw_end512 B header_copy copia de 0x0 Copia exacta del header completo. El bootloader la verifica en el segundo stage
EOF − 44 B trailer C6 18 C6 18 Secuencia mágica al final del archivo. Si se sobreescribe con 00 00 00 00 → el bootloader rechaza el firmware

⚠ Por qué se pierde el trailer:
La función _fix_integrity() original leía el trailer con data[-4:] después de extender el archivo con ceros. Esto hacía que saved_trailer = b'\x00\x00\x00\x00'. El fix correcto: leer el trailer al inicio de la función, antes de cualquier resize.

§4 — Struct de Settings en RAM (0x0301D140)

El puntero 0x0301D140 está hardcodeado como literal en el pool de la función dispatch. Apunta al struct de configuración activa en RAM donde el firmware almacena el tema actual.

Cómo se accede en ARM: LDR R2, [PC, #0x3C0] → carga 0x0301D140 desde el pool literal (PC-relative).
LDRB.W R2, [R2, #0x34F] → lee el byte en 0x0301D140 + 0x34F = 0x0301D48F → ese byte es el theme_index.

§6 — Estrategia de Patching

6.1 — Patch para 5 temas (A-E) — solo ADDW + CMP

Con NEW_BLK = 374 (40 POWERON + 6 CHARGELEVEL + 1 POWEROFF + 327 UI), los 4 slots existentes bastan para temas B,C,D,E. No se necesita code cave.

✓ PATCHED 5 temas — NEW_BLK=374

; umbral=0 (todos)
00 F2 76 10
ADDW #374
; B = 1×374
00 F2 EC 20
ADDW #748

00 F2 D8 50
ADDW #1496

00 F2 62 40
ADDW #1122

Por qué E (hw=4) tiene ADDW=4×374=1496 pero D (hw=3) tiene ADDW=3×374=1122:
El tema_index no es el número de bloque, es el índice de hardware del tema. Cada tema mapea a su bloque como ADDW = hw_index × NEW_BLK. En el firmware original el orden de los CMP era E antes que D (herencia del diseño original), y al parchear se conserva ese mismo orden pero con las fórmulas correctas.

6.2 — Patch para 6 temas (A-F) — B.W + Code Cave

El quinto tema no-default (F, hw_index=5) no tiene slot en el dispatch de 4 entradas. Se inyecta un B.W (Branch.Wide, 4 bytes) que salta a una cave en ceros a 0x13D90.

6.3 — Code Cave (file 0x13D90, virt 0xFF813D90) — 72 bytes

§7 — Referencia de Codificación ARM Thumb2

Instrucciones clave usadas en el proyecto, con sus patrones de bits y ejemplos concretos.

CMP Rn, #imm8 — Thumb 16-bit (T1)
Formato: [ 0010 1 Rn(3) | imm8(8) ] Siempre 2 bytes, Rn=000 para R0
CMP R0,#0x43: 0x43 0x28 → imm8=0x43, byte 2=0x28 (0010 1 000)
CMP R0,#0x00: 0x00 0x28 → imm8=0x00
ADDW Rd, Rn, #imm12 — Thumb2 32-bit (T4) — formato "modified immediate"
HW1: [ 1111 0 i 1 0 0000 Rn(4) ] Para ADDW siempre: 0xF200 (i=0, op=0b0000, Rn=R0=0000)
HW2: [ 0 imm3(3) Rd(4) | imm8(8) ] imm12 = i:imm3:imm8 — Rd=R0=0000
ADDW #374: F2 00 | 76 10 → HW2=0x1076: imm3=001, Rd=0000, imm8=0x76; i=0 → imm12=0x176=374 ✓
ADDW #748: F2 00 | EC 20 → HW2=0x20EC: imm3=010, imm8=0xEC → 0x2EC=748 ✓
ADDW #1122: F2 00 | 62 40 → HW2=0x4062: imm3=100, imm8=0x62 → 0x462=1122 ✓
ADDW #1496: F2 00 | D8 50 → HW2=0x50D8: imm3=101, imm8=0xD8 → 0x5D8=1496 ✓
ADDW #1870: F2 00 | 4A 50 → HW2=0x504A: imm3=101, imm8=0x4A → 0x54A=1354? — usa fórmula completa
B.W (Branch Wide) — Thumb2 32-bit — el más complejo
HW1: [ 1111 0 S | imm10(10) ] S = signo del offset
HW2: [ 1 J1 1 J2 | imm11(11) ] J1 = NOT(I1 XOR S); J2 = NOT(I2 XOR S)
Offset: SignExtend( S:I1:I2:imm10:imm11:'0' ) offset es relativo a PC+4 (instrucción siguiente)
Ejemplo: D5 F7 19 BF → HW1=0xF7D5, HW2=0xBF19 → salta de 0x3DF5E a 0xFF813D90 (cave)
LDRB.W Rt, [Rn, #imm12] — Thumb2 32-bit (T2 unsigned offset)
HW1: [ 1111 1000 1001 Rn(4) ] = 0xF892 para Rn=R2
HW2: [ Rt(4) | imm12(12) ] = 0x234F para Rt=R2, imm12=0x34F
Bytes: 92 F8 4F 23 → LDRB.W R2, [R2, #0x34F] — lee theme_index desde settings struct
LDR Rt, [PC, #imm8×4] — Thumb 16-bit PC-relative (T1)
Formato: [ 0100 1 Rt(3) | imm8(8) ] PC es alignado a 4 bytes (PC+4 & ~3)
Ejemplo: F0 4A → Rt=R2(010), imm8=0xF0 → pool = (0x3DF60 & ~3) + 0xF0×4 = 0x3DF60 + 0x3C0 = 0x3E320
CBZ Rn, label — Thumb 16-bit (T1, forward only)
Formato: [ 1011 0 i 1 imm5(5) Rn(3) ] offset = i:imm5:0 (7-bit, siempre positivo)
Bytes: A2 B1 → 0xB1A2 = 1011 0001 1010 0010 → i=0, imm5=10100, Rn=R2 → offset=+0x28

§8 — Boot/Charge/Shutdown por tema (estructura)

Cada tema tiene su propio conjunto de animaciones de boot, carga y apagado.
Estas se identifican por nombre: POWERON{n}, CHARGELEVEL{n}, POWEROFF0 donde el nombre refleja el orden dentro del bloque del tema.
El patch de boots por tema modifica la tabla de metadatos para que cada tema apunte a sus propias frames en lugar de compartir las del tema A.
